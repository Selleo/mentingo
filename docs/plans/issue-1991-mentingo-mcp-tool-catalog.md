# Issue #1991: Mentingo MCP tool catalog

Planning contract for [Add Mentingo MCP](https://github.com/Selleo/mentingo/issues/1991). This catalog describes the tools an agent should see, their intended behavior, and the Mentingo boundaries an implementation must preserve. The tools are **proposed**, not available in the current API. The baseline for this document is `origin/main` at `f7ad79359`.

## Product goal and boundary

An authorized editor connects Claude, Codex, or another MCP client to Mentingo and asks it to inspect or change courses, chapters, lessons, knowledge base articles, news, Q&A, or development paths. Mentingo is the server and the source of truth. An MCP tool translates a focused request into existing domain services; it never grants more access than the same user has in Mentingo.

The catalog covers these authoring and management domains. Development paths are called learning paths in the API. Enrollment, exports, learner analytics, and learning progress are separate capabilities and are outside this authoring catalog. Course publication and deletion remain explicit, high-impact operations. Pricing and course behavior settings are in scope because they are part of course management.

## Agent instructions

These instructions should be adapted into the MCP server's `instructions` field and tool descriptions:

1. Start with the relevant `list_*` or `get_*` tool before changing an existing entity. For course structure, call `list_chapters`, then `list_lessons` or `get_lesson` as needed. Use IDs returned by Mentingo, not titles or guessed IDs, as mutation targets.
2. State the content language explicitly. Use an entity's base language for structural changes; edit localized text in an available language without changing shared structure. Never infer a language from the user's prompt when the entity already defines one.
3. Prefer the smallest operation that fulfills the request. Codex plans and drafts in its own conversation, then uses these direct Mentingo tools to save each approved change. Do not require a Mentingo AI authoring session, proposal, export, or apply workflow.
4. After a write, use the returned entity ID and revision to read back the changed entity. Treat a conflict as a request to reread and ask the user how to proceed; do not overwrite concurrent edits silently.
5. Before publishing or deleting content, or deleting a parent with children, show the user the exact affected entity and impact. The tool requires a current revision and explicit confirmation information; client approval alone is not a substitute for server validation.
6. Never pass browser cookies, access tokens, tenant IDs, user IDs, hidden grading criteria, or prompt internals through tool arguments or tool results. The server derives identity and tenant from the authenticated connection.

## Common contract for every tool

- **Identity:** The tenant-hosted `/api/mcp` endpoint accepts a Mentingo MCP access token obtained through user OAuth. The token is bound to this resource, user, tenant, client, scopes, and expiry. The user's web session may support the login and consent screen, but is not the MCP credential. A future automation credential is a separately scoped identity, not the existing broad integration admin key.
- **Session and authorization:** Validate token signature or introspection, audience, expiry, revocation, client grant, user status, tenant status, and tenant membership on connection initialization **and every HTTP request**. Re-resolve the user's current Mentingo roles and permissions for **every tool invocation**, then check the target entity's ownership/manageability, feature gate, and language. A long-running job rechecks access before applying a write. An MCP protocol session ID is only transport state: it never authorizes a call, keeps a revoked grant alive, or caches a permission snapshot. `tools/list` may hide unavailable tools for convenience, but every `tools/call` is independently enforced. Run tenant database work in the existing RLS context. Do not use caller-provided `tenantId` or `userId` to select a tenant or actor.
- **Language:** `language` is a value from `SUPPORTED_LANGUAGES` and must belong to the target entity's available locales when reading or editing localized fields, except when adding a new locale. Structural create, delete, and reorder operations use the base language. Responses identify both requested and base language. Keep each domain's existing manager fallback and learner/public locale rules.
- **Inputs:** UUIDs identify entities. Mutation inputs are narrow and validated against the corresponding domain schema; no arbitrary database patch, raw SQL, opaque HTTP proxy, or unrestricted HTML/file URL argument. Optional `expectedRevision` is an opaque revision returned by a read, backed by a stable timestamp or content hash. Add this check where the existing service lacks one.
- **Results:** Return concise `structuredContent` with entity `id`, parent ID where relevant, `language`, `revision`, changed fields or ordered child IDs, and a user-openable URL. Paginate lists and bound text size. Do not return learner data, secrets, internal prompts, or full rich content in a list result.
- **Errors:** Distinguish `unauthorized`, `forbidden`, `not_found`, `unsupported_language`, `validation_failed`, `conflict`, `feature_unavailable`, and `operation_failed`. Never report a mutation as complete when a queued job is only accepted.
- **Writes:** Record actor, client, tool, entity, outcome, and request ID in the existing audit/event pattern. Use an idempotency key for retryable creates and queued operations. Reuse existing domain validation, queues, and outbox behavior instead of duplicating persistence in the MCP adapter.
- **Tool annotations:** Mark reads as read-only. Mark writes as mutating, and deletes as destructive. These hints help clients choose approvals; server authorization and confirmation remain authoritative.

`get_my_capabilities` is a read-only discovery tool. On each call it reports the authenticated user's currently available authoring domains and operations after rechecking the grant, current permissions, tenant and feature settings. It never accepts a user or tenant ID. Its output helps the agent choose tools; it does not authorize later calls.

### Files and asset-backed authoring

For locally running agents such as Codex CLI, use Mentingo's existing multipart and TUS upload routes. The agent reads the local file and sends its bytes to the API; the remote MCP server does not read a local path or relay file bytes. An authenticated MCP tool first issues a short-lived upload grant for one intended file and target. Its response includes a complete `uploadUrl` derived from the MCP tenant resource URL and exact request instructions, so Codex never has to guess an API host. New grants use a prefixed Bearer token recognized by the upload guard. Codex uses that grant only at the returned upload endpoint, so it does not need a separate broad API credential or access to the MCP client's OAuth token. The grant is an upload capability, not a general API key: bind it to the actor, tenant, target entity, upload kind, allowed route/method, declared filename/MIME/size, expiry, and a single upload or resumable session. Check current permission and target ownership when issuing it and again before attaching or finalizing a file. Do not log the grant or accept it on unrelated API routes.

Existing routes include `POST /api/lesson/upload-files-to-lesson`, `POST /api/articles/:id/upload`, `POST /api/news/:id/upload`, `POST /api/file`, video upload initialization and TUS endpoints under `/api/file/videos`, and SCORM import initialization and TUS endpoints under `/api/scorm/import`. Lesson uploads create a resource record; `insert_lesson_resource` uses its returned resource ID and attaches it through the native content update. Article and news uploads follow their native resource handling. Use their returned resource or file IDs in subsequent authoring tools where needed. Video and SCORM processing remains asynchronous; poll the existing status route or expose a narrow status tool only if the current API does not give the local agent a usable status check.

The upload API accepts multipart grants only for the bound route and operation and consumes them on the first request. Resumable Mentingo grants remain usable only for their bound session paths until the native session ends or the grant expires; offset and completion requests recheck current permission and target access. Native MIME and size validation still applies. Course covers, certificate signatures, localized article/news covers, development-path media, and AI Mentor avatars attach through their existing domain routes. Bunny returns provider-scoped upload headers from native initialization, so those bytes go directly to Bunny. A grant returned as a tool result can be visible in the agent's context, so it must have minimal authority and a short lifetime. Clients with no local file and HTTP access need a separate upload integration; that is outside this local-agent flow.

Multipart `create_scorm_course` also accepts an optional thumbnail description. The returned grant names the additional `thumbnail` file field and binds both files. Resumable SCORM import accepts the native package-only flow; an image can instead be uploaded through `request_generic_file_upload` before import or through `request_course_upload` after import.

## Distribution and client setup

- **Direct Codex setup:** Once the HTTPS endpoint and OAuth discovery are live, document `codex mcp add mentingo --url https://<tenant-host>/api/mcp`, `codex mcp login mentingo`, and `codex mcp list`. The host name is a deployment placeholder, not a fixed URL. This path needs no published npm package or marketplace listing. Codex is the MCP host/client; Mentingo hosts the server.
- **Plugin directory:** A public listing is optional and later. Submit Mentingo as a remote MCP-backed plugin through OpenAI's plugin submission portal using the public HTTPS endpoint, verified publisher/domain, accurate tool metadata and annotations, and review materials. Approval and publication are separate steps. A plugin package may add skills or install metadata, but does not replace the hosted MCP server.
- **Client coverage:** The direct upload workflow above assumes a locally running agent with filesystem and authenticated HTTP access. A hosted ChatGPT/Codex plugin session may lack those local capabilities. Before marketing file-authoring tools there, verify a supported file-transfer path for that surface; otherwise describe the plugin's available authoring scope accurately.

## Implementation map and delivery gates

- **MCP transport:** Add a Nest module backed by the official TypeScript MCP server SDK and Streamable HTTP at a stable HTTPS `/api/mcp` URL on each tenant host. Keep tool definitions thin. MCP protocol sessions are distinct from login sessions; there is no Mentingo AI authoring session in this design.
- **OAuth:** Add standards compliant MCP resource metadata, authorization server discovery, consent, PKCE code flow, token issuance/refresh/revocation, audience checks, and client registration support that works with Codex and Claude. Reuse Mentingo sign-in for user identity. Do not reinterpret the existing Google/Microsoft login callback or integration admin API key as a complete MCP authorization server.
- **Tenant and permissions:** The global JWT and permission guards plus the tenant RLS interceptor in `apps/api/src/app.module.ts` need an explicit MCP authentication path that produces a trusted `CurrentUserType` before domain work. Recheck live permission grants on every tool call, not just login or MCP initialization. Discovery and authorization endpoints have their own public handling. Never bypass RLS for a tool call.
- **Direct API adapters:** Implement each MCP tool as an adapter to the existing API's validated domain behavior. In the same Nest process, call the underlying domain services with the authenticated actor and existing guards/validators; do not call one controller from another. If deployed as a separate MCP process, use only the existing authenticated API contracts, with a user-bound token, and never proxy arbitrary paths. Fill narrow gaps such as revision checks, idempotency, and safe article creation in the native API before advertising those tools. Keep binary uploads on existing API routes with the narrow grants described above. Codex composes the edits; Mentingo validates and stores them.
- **Activity and jobs:** Preserve each domain's existing outbox activity events, search index updates, queue processing, and attachment rules. A background job rechecks actor/tenant/permission when it performs a write. Return queued status as queued, then expose a status tool when a native operation is asynchronous.
- **Release sequence:** First deliver OAuth, live permission checks, capability discovery, and read tools; then direct course/chapter/content lesson CRUD and settings; then articles, news, Q&A, and development paths with their locale and ownership rules; then type-specific lessons, media, and high-impact deletion/publication. Ship each stage only when Codex and Claude can connect and the tool behavior is covered by tenant, permission-revocation, locale, conflict, retry, and destructive-action checks.

### Required permission scenarios

- A user who loses a role, tenant membership, or OAuth grant after initialization is denied on the next `tools/call`, even when the same MCP session ID is reused.
- An own-only editor cannot read another author's drafts through manager tools or mutate another author's course, article, news post, or development path.
- A Q&A editor with only `QA_MANAGE_OWN` is denied Q&A writes until the product implements a real own-entry policy; `QA_MANAGE` works.
- A path editor with path metadata permission but no path-course permission cannot add, remove, or reorder its courses.
- A tenant feature switch disables its tools even when the user still holds a matching permission; a queued operation checks the switch again before mutation.
- A token for another audience, expired token, revoked token, or client grant without the relevant scope is rejected before entity lookup.
